# P1 / P2: объём и приёмка

Продолжение архитектурного аудита после P0. Сохраняются монолит, SQLite,
один основной агентский цикл и 18 бизнес-инструментов.

## P1

- Единый исполняемый каталог возможностей: аргументы, обязательность,
  допуски, причины отказа, зависимости, инвалидирование и контекст FAQ.
  Неизвестный инструмент без политики запрещён.
- Охват поиска: источники, страницы, свежесть, выполненные/неизвестные
  проверки, бюджет, причины неполноты. Отказ страницы не означает конец рынка.
  Совпадение имеет доказательство; пустой результат относится к проверенному охвату.
- Повторяемые регрессии ошибочных ответов, генерируемые последовательности,
  отложенные формулировки, повторные прогоны модели и версии в отчётах выпуска.
- Право телефонной операции связано с владельцем, квартирой и ID решения;
  квоты и синтез ограничены операцией. Общие SIP-учётные данные нельзя считать
  одноразовыми: публичная телефония не открывается автоматически.

## P2

- Ограниченные очереди и память процесса; промежуточный прогресс объединяется.
  Медленный SSE-клиент восстанавливается из сохранённых событий без потери фактов.
- Обновления UI и решения не ждут озвучку, телефонное аудио или декоративную паузу.
- Явные версионированные миграции с журналом и проверкой совместимости.
- Раздельные liveness/readiness и состояние отдельных возможностей.
- Метрики задержек, очередей, разбора, сохранения, непроверенных результатов
  и восстановления без клиентских текстов и меток высокой кардинальности.
- Измерение нагрузки на текущей SQLite; смена БД/несколько workers только
  при подтверждённой необходимости, без добавления инфраструктуры по умолчанию.

## Приёмка

Все прежние регрессии P0 сохраняются. Дополнительно: согласованность каталога,
закрытый допуск нового инструмента, различимые неполный/пустой/недоступный поиск,
запрет чужого/устаревшего телефонного разрешения, квоты TTS, медленный SSE,
неблокирующая озвучка, обновление старой SQLite и отказ при неизвестной миграции,
различение живого процесса и недоступной возможности, ограниченность метрик,
повторный и отложенный экзамен модели. Выкладка — после изолированного стенда
и резервной копии; реальные телефонные вызовы при испытаниях не выполняются.

## Реализация

| Возможность | Где находится |
| --- | --- |
| Каталог 18 инструментов, требования, причины отказа и единицы аргументов | `backend/agent/capabilities.py`, регистрация и диспетчер `actions/__init__.py` |
| Один набор полей для инвалидирования профиля | `CORE_FIELDS` / `FILTER_FIELDS`, применение в `actions/request.py` |
| Отчёт об источниках, страницах, свежести, доказательствах и неизвестных признаках | `backend/agent/coverage.py`, `sources`, `conditions.py` |
| Общий бюджет сетевой выдачи, различение отказа страницы и отсутствия новых результатов | `sources/__init__.py`, `actions/search.py` |
| Ограниченные SSE-очереди, объединение прогресса, восстановление фактов из SQLite | `backend/events.py`, `main.py`, `persistence.py` |
| Ограниченные очереди команд/FAQ, число работающих диалогов и кэш владельцев | `commands.py`, `session.py`, `main.py` |
| Независимое применение UI и последовательное воспроизведение аудио | `frontend/js/effects.js`, `app.js` |
| Неизменяемые manifests схемы и журнал версий | `backend/db/migrations.py`, `schema_v1.json`, `schema_v2.json` |
| Проверка процесса, готовности и метрики без клиентских текстов | `readiness.py`, `telemetry.py` |
| Разрешение телефонной операции и расход синтеза | `phone_access.py`, `main.py`, `frontend/js/phone.js` |
| Версии, сохранённые ошибки модели, повторный и отложенный экзамен | `release.py`, `scripts/check_release.py`, `tests/data/model_incidents.json`, `tests/e2e/semantic_eval.py` |

Схемы аргументов берутся из зарегистрированных функций; обязательные аргументы
выводятся из сигнатур. Политика допуска общая для предложения инструментов модели,
исполнителя и информационных ответов. Отказ содержит конкретное невыполненное
условие. Регистрация без политики не открывает новый инструмент модели.

Охват относится к полученным объявлениям, а не ко всему рынку. Сетевой поиск имеет
общий бюджет, включая следующие страницы и варианты запроса. Истечение бюджета
не превращает сохранённый срез в свежий. Карта, сведения продавца и неизвестные
признаки различаются по источнику и времени; отсутствие проверки не означает
отсутствие поликлиники. В интерфейсе подробности доступны рядом с подборкой.

Переполнение очереди SSE закрывает медленного подписчика сигналом восстановления.
Браузер повторяет чтение с последнего применённого события; критические события
остаются в SQLite. Отказ очереди команд происходит до принятия новой команды,
повтор с прежним ID сохраняет идемпотентность. Подключённый владелец диалога не
вытесняется из кэша. Полная история остаётся в БД, в памяти ограничен её хвост.

Liveness (`/api/health/live`) проверяет процесс. Readiness (`/api/health/ready`)
проверяет доступность БД, версию схемы, конфигурацию модели, недавние отказы и
ёмкость обработчиков. Статус внешних возможностей показан отдельно. Проверка
пассивная: HTTP-зонд не делает платную генерацию и не обещает успешность следующего
запроса провайдеру. Метрики (`/api/metrics`) относятся к одному процессу, используют
фиксированные имена и ограниченное число рядов; тексты, ID и аргументы клиента
не являются метками. После перезапуска счётчики процесса начинаются заново.

## Граница реальной телефонии

Доступен ограниченный операторский режим с настроенным PIN. Разрешение связано
с владельцем диалога, актуальной карточкой, квартирой и операцией; повторное
получение по той же карточке запрещено. Ограничены срок звонка, число разрешений
за час и символы TTS; чужой токен не работает. Без PIN режим закрыт.

Общие SIP-учётные данные оператора не являются одноразовыми. Получивший их
доверенный оператор технически может использовать SIP вне интерфейса, поэтому
ограничения приложения не объявляются полной защитой публичного телефонного
доступа. Перед его открытием нужны изолированные учётные данные провайдера с
отзывом либо контролируемый сервером набор номера. В Exolve управление SIP ID
есть, но создание может подключать тарифицируемый ресурс — см.
[официальную документацию SIP API](https://exolve.ru/docs/ru/api-reference/sip-api/).
Новые ресурсы и настоящие вызовы при этой работе не создаются.

## Повторяемая проверка выпуска

```bash
.venv/bin/python scripts/check_release.py --report-dir /tmp/mesto-release
# Дополнительно расходует квоту модели на синтетические запросы:
.venv/bin/python scripts/check_release.py --report-dir /tmp/mesto-release-live --live --provider gigachat --repeat 2
```

`--node /absolute/path/to/node` задаёт Node, если его нет в PATH. Неживой прогон
не выдаётся за экзамен модели: поле `model_exam` в отчёте явно различает режимы.
Повторный корпус — 31 × 2 запроса; отдельно 10 отложенных формулировок. Ошибка
хотя бы одного случая делает критерий выпуска непройденным. В отчёте сохраняются
версии промптов, контрактов, расчётной политики, схемы и backend, а также фактически
ответившее имя модели. Тексты тестов синтетические; пользовательская БД и реальные
телефоны не участвуют. Нагрузочный сценарий отдельно проверяет 8 диалогов ×
16 команд, SQLite и очереди; его время не включает задержку внешней модели.

Сохранён и воспроизводится случай, найденный повторным прогоном: цитата
«Новгород» внутри «Новгороде» разворачивается до полного исходного слова для
сопоставления, без достраивания названия города. При неоднозначности следует
вопрос о Нижнем/Великом Новгороде, а не изменение города по догадке модели.

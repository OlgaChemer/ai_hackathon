# Защита агента

Защита снижает вероятность prompt injection и ограничивает последствия. Фильтр слов, JSON и инструкции модели не гарантируют, что модель никогда не поддастся атаке. Границы полномочий задаёт серверный код.

## Что проверяет код

- Действия доступны только через реестр `backend/agent/actions`. Нет инструментов произвольного SQL, shell, чтения файлов или отправки писем.
- До выполнения проверяются типы, enum, числовые диапазоны, неизвестные/обязательные параметры, размеры строк и коллекций. `validation.py` реализует используемое действиями подмножество JSON Schema, а не универсальный валидатор.
- Поиск и звонок требуют подтверждённых рамок; цена, выбор объекта и подписание — отдельного решения клиента. Параметр `approved`, придуманный моделью, не даёт согласия: его нет в схеме инструментов.
- Изменение основных условий запроса сбрасывает предыдущие звонки, согласованные цены, выбранную квартиру и финансовые расчёты. Изменение бюджета на карточке рамок также сбрасывает старые согласия.
- Лимит торга проверяется кодом переговоров. Модель может ошибиться в речи; текстовые заявления модели сами по себе не являются подтверждением сделки.
- Не более 14 вызовов инструментов без очередного сообщения клиента, включая вызовы внутри одного ответа. Размер ответа ограничен настройками модели и выходным фильтром.
- Третье подряд одинаковое действие без нового ответа клиента останавливается. Активная работа хода ограничена `AGENT_TURN_TIMEOUT_S` (120 секунд); ожидание человека исключено. При остановке операция отменяется, незавершённые вызовы получают результат «прервано», продолжение требует сообщения клиента.
- Очередь GigaChat ограничена 6 ожидающими генерациями и 25 секундами ожидания по умолчанию; сам вызов модели с OAuth/повторами — 60 секундами. Переполнение не вызывает автоматического бесконечного повтора. Настройки и ограничения одного процесса описаны в README.
- Владение диалогом проверяется до чтения, подтверждения карточки и передачи реплики продавца. Новая таблица аудита добавляется штатным `create_all`; существующая база не переименовывается и не сбрасывается.

## Вход, контекст и выход

`guard.check_input` распознаёт известные попытки смены инструкций, извлечения секретов, массового повторения и некоторые явные фрагменты вредоносного кода. Нормализация учитывает невидимые символы и часть похожих латинских/кириллических букв. Это дополнительная эвристика; SQL защищается параметрами ORM, HTML — экранированием на фронтенде.

Проверяются первый запрос, продолжение диалога после перезапуска, сообщения, реплики продавца, все текстовые поля ответов на карточки. Отклонённое подтверждение возвращает 422 и оставляет карточку открытой. Пять отклонённых сообщений в живой сессии за две минуты включают паузу для сообщений, карточек и продавца. Перезапуск процесса сбрасывает этот счётчик.

Адреса, пожелания, сведения продавца, состояние сделки и контекст ответов не вставляются в системные инструкции. Они передаются отдельными JSON-сообщениями `user` с полями `source`/`data`; результат инструмента остаётся `tool`. Системная политика объясняет, что это данные. Известные команды в них скрываются, но неизвестные формулировки могут остаться. Одного разделения ролей недостаточно для абсолютной защиты.

Выход проверяется перед записью событий и отправкой SSE: обычные ответы, карточки, варианты, реплики звонка, факты, ключи словарей. Старая история проверяется при воспроизведении. Память модели проверяется перед сохранением и передачей. Фильтр ищет служебную метку, известные фрагменты инструкций, характерные форматы секретов и значения настроенных ключей API. Он не гарантирует обнаружение перефразированных инструкций, неизвестных персональных данных или закодированного секрета.

В журнал безопасности идут категория, место, идентификаторы сессии/пользователя, SHA-256 и длина текста. Исходный текст и ключи в `security_events` и security-лог не записываются. Старые записи базы автоматически не чистятся.

## Частота запросов

Лимиты действуют одновременно по IP и, при наличии проверенной авторизации, по аккаунту. Cookie `vid` не определяет лимит. Создание сессии сопоставляется по точному пути; лимит вложенных маршрутов отдельный.

| Маршрут | Лимит |
| --- | --- |
| POST `/api/session` | 10 / 10 минут |
| POST `/api/chat/…` | 30 / минуту |
| POST `/api/session/…` | 60 / минуту |
| POST `/api/stt`, `/api/tts` | по 40 / минуту |
| POST `/api/auth/…` | 20 / 10 минут |
| GET `/api/phone` | 30 / минуту |

Превышение возвращает 429 и `Retry-After`. Истёкшие счётчики удаляются, память ограничена 10 000 счётчиков. Это реализация для одного процесса: для нескольких workers/серверов нужен общий счётчик, например Redis. Пользователи за одним NAT делят лимит IP. За reverse proxy следует доверять forwarded-заголовкам только от адреса этого proxy в настройках ASGI-сервера; приложение самостоятельно не берёт IP из присланного `X-Forwarded-For`.

HTTP-ответы содержат `nosniff`, запрет iframe и ограничения доступа к микрофону/камере. Для статических файлов включена проверка кеша через `Cache-Control: no-cache`.

## Проверка

См. [TESTING.md](TESTING.md). Тесты с поддельной моделью проверяют границы кода даже при небезопасном ответе модели. Отдельный opt-in smoke test проверяет реальный LLM на синтетических примерах, не выполняя выбранные инструменты. Его успех не является измерением общего процента защищённости.

# Понимание запросов и разнообразные диалоги

## Выбор архитектуры на GigaChat Ultra

На одном зафиксированном варианте кода (`2155de2`) сравнили три режима с настоящими GigaChat Ultra и Цианом. Каждый получил одинаковые пять сценариев (восемь этапов) без исправляющих подсказок. Дополнительно проверяли вопрос при открытой карточке и защиту от инъекции.

| Вариант | Полностью пройдено сценариев | Наблюдение |
| --- | --- | --- |
| Основной агент сам извлекает параметры | 0/5 | Пропуск оплаты/рынка, добавленные ограничения, угадывание города, повторы действий. |
| Один структурированный разбор перед основным агентом | 3/5 | Лучше сохраняет параметры; старый контракт терял желательность парка и угадывал неоднозначный город. |
| Разбор и отдельный независимый проверяющий | 0/5 | Расхождения двух ответов приводили к отказам даже при корректном запросе; появились лишние обращения к модели. |

Это небольшой эксперимент с конкретными контрактами, а не статистический рейтинг моделей. После него выбран один разбор, исправлен его контракт, удалён отдельный проверяющий. Сложность перенесена из цепочки моделей в небольшой типизированный протокол и проверки состояния. Самооценка уверенности не используется: процент от самой модели не даёт гарантии правильности.

## Текущий путь сообщения

1. Модель получает принятый новый ввод, контекст открытого уточнения, прежний профиль и каталог территорий. Предложения основного планировщика не служат источником пожеланий.
2. GigaChat возвращает один ответ по нативной JSON Schema (`response_format.type=json_schema`, `strict=true`). Обычные параметры — фиксированные nullable-поля. Неназванное поле равно `null`; оно не перезаписывает профиль. Условия вместе с приоритетом обозначаются как обязательные, желательные или снятые.
3. Код проверяет типы, диапазоны, принадлежность каталогу и актуальность сообщения. Команда продолжения, остановка и информационный вопрос не имеют права менять профиль. Изменения применяются целиком; неоднозначность вызывает уточнение без частичной записи.
4. Основной агент выбирает действия по обновлённому состоянию. Подтверждения цены, звонка и сделки остаются отдельными решениями пользователя.

Обычно добавляется **одно** обращение к модели на новое свободное сообщение. Повтор разрешён только один раз при некорректном формате. Результат кэшируется для сообщения и исходного профиля; действия планировщика повторно его не интерпретируют. Устаревший ответ отбрасывается, если за время запроса поступил новый ввод или изменился профиль. Это не независимая проверка смысла: ошибочное толкование моделью по-прежнему возможно.

Свободный текст не разбирается набором регулярных выражений. Для территорий модель выделяет исходные слова и начальные формы; код сопоставляет их со справочником, не достраивая неназванные части. Общая часть нескольких названий требует уточнения; короткий ответ может разрешить один из уже предложенных вариантов. Справочник синонимов выделенного топонима и разбор страниц Циана остаются техническими задачами, отдельными от понимания реплик.

## Прогресс и согласия

Если клиент просит искать или продолжить, условия заполнены, а агент только обещает действие или повторяет обновление без прогресса, контроллер запускает разрешённый поиск по состоянию. После поиска показывает подборку либо варианты изменения условий. Для этого не ищутся слова «сейчас начну» в ответе модели. Число повторов и время работы ограничены. Это правило не разрешает автоматически звонить, согласовывать цену или подписывать документы.

Информационный вопрос не закрывает текущую карточку. Остановка блокирует поиск и звонки. После снятия ограничений пул пересобирается из исходных объявлений.

## Воспроизводимые сценарии

```sh
.venv/bin/python -m tests.e2e.live_dialogue_cases --base URL
.venv/bin/python -m tests.e2e.live_site --base URL --case cash --until selection
.venv/bin/python -m tests.e2e.live_site --base URL --case cash --until sign
.venv/bin/python -m tests.e2e.live_controls --base URL
```

Живые тесты расходуют квоту и создают синтетические диалоги. Полный сценарий выбирает только ИИ-продавца, без телефонных вызовов; подписание демонстрационное. Проверяются профиль, параметры обращений к источнику и выдача, а не только ответы агента. Ошибочные ответы не исправляются подсказками.

| Сценарий | Проверка |
| --- | --- |
| «Однушка или двушка», «пять с половиной лямов», «наличка» | Обе комнатности, 5 500 000 рублей, вторичка, наличные. |
| 1 или 3 комнаты, без двухкомнатных | Сохраняются [1, 3], а не диапазон [1, 2, 3]. |
| Москва или область → только Казань | Меняется территория, сохраняются бюджет, комнаты, оплата и рынок. |
| Желательный парк, запреты первого/последнего этажей → снять парк, разрешить первый | Отменяется парк вместе с желательностью; запрет последнего этажа остаётся. |
| Неоднозначный «Новгород» → Великий, не Нижний | До уточнения город не угадывается; после него запрашивается правильный город. |

Дополнительные проверки: вопрос об эскроу сохраняет карточку, корректировка в вопросительной форме меняет город с сохранением бюджета, просьба остановиться не вызывает поиск/звонок, команды продолжения не расширяют комнатность.

## Регрессия примеров на главной, 03.11.2026

После предыдущего выпуска реальный запрос из собственного примера интерфейса «Ищу двухкомнатную квартиру в Москве до 15 млн ₽» дважды отклонялся. Лог сессии `9c41e1e50667` показал ошибку буквального происхождения названия. Локальное воспроизведение трижды вернуло `source=Москва` вместо исходного `Москве`; в двух ответах модель также выдала `rooms=20`. Проверки пяти сложных запросов не покрывали этот простой неполный запрос. Браузерная проверка примеров использовала подменённую модель и не могла выявить эту ошибку настоящего Ultra.

Исправление `87cd19f`:

- Буквальные исходные слова предлагаются модели как `enum` в нативной схеме. Она выбирает `Москве`, а в отдельном поле нормализует до `Москва`. Словарь строится из слов сообщения без извлечения комнат, оплаты или города правилами. Проверка неоднозначности территории сохранена.
- У поля одного числа комнат устранён ошибочный минимум 6, который исключал ответ 2. Обычные комнатности снова допустимы; альтернативы остаются массивом.
- Неуказанная числовая граница (`value=null`) не отклоняет весь запрос и не отменяет прежнее условие. Например «рядом с метро» сохраняется в пожеланиях без выдуманного количества минут.
- На главную добавлена кнопка «Разговор», подключённая к существующему `Talk`. Она открывает новый чат и включает микрофон в обработчике нажатия; первая распознанная фраза создаёт подбор. Кнопка диктовки остаётся отдельной.

Новая проверка `tests.e2e.live_welcome_inputs` читает все шесть примеров непосредственно из HTML и отправляет их настоящему Ultra. Проблемный пример повторяется ещё дважды. Все 8 разборов прошли локально и на изолированном серверном стенде. Модульные проверки: 220/220 локально и на сервере. Браузерная проверка 1440/390 px использует настоящий `Talk` с поддельным микрофоном Chromium: включение, передача распознанной фразы в новый диалог и завершение разговора прошли. Качество STT и работа реального iPhone этим тестом не проверяются.

На том же серверном кандидате после исправления повторно прошли все пять разнообразных сценариев (8/8 этапов), контроль FAQ/смены города/остановки и полный путь проблемного примера до 10 карточек. После обновления публичного сайта точный запрос со скриншота также дошёл до 10 московских двухкомнатных квартир с бюджетом 15 млн; диалог `1ae9b97504b7`. При необходимости тестовый клиент отвечал на вопросы об оплате и рынке; первоначальные город, комнаты и бюджет сохранялись.

## Начальный лимит, порядок финансов и повторы, 03.11.2026

В диалоге `c2b5a9b81d92` способ покупки не был известен до карточки звонка. После выбора наличных модель чередовала уже выполненный `mortgage_programs` с повторными `update_request`, затем повторяла расчёт подряд. Каждое выполнение заново отправляло одну и ту же фразу. Старый ограничитель останавливал лишь последовательные одинаковые вызовы. Отдельная карточка лимита перед звонком соответствовала прежнему сценарию; пользователь изменил правило на подтверждение один раз в начале и после изменения суммы.

Код `c44b9cb`:

- Контроллер требует явное начальное подтверждение лимита и известный способ покупки перед первым поиском. Он не подтверждает карточки за пользователя. Изменение суммы отзывает согласие; город, комнаты, рынок и пожелания сохраняют его, но сбрасывают прежнюю подборку и согласия по конкретным объектам.
- Подтверждённая сумма сохраняется в служебных данных профиля и восстанавливается после перезапуска. Для старого формата читаются только доверенные результаты серверного инструмента подтверждения, без извлечения согласия из свободного текста. Эти метаданные не передаются модели и в UI-профиль.
- Финансовый расчёт имеет ключ исходных параметров. Повтор возвращает готовый результат без сообщения и панели; выполненный расчёт не предлагается модели повторно. Для наличных ключ зависит только от суммы и способа оплаты; этот результат также сохраняется для восстановления. Повторное обновление профиля не предлагается модели без нового ввода клиента.
- Клиент игнорирует повторно доставленные события с тем же номером; одинаковые соседние сообщения агента схлопываются и при воспроизведении старой истории. Сохранённая история в БД не переписывается.
- Enter на главной отправляет запрос, Shift+Enter переносит строку. CSS, входной скрипт и все ES-модули получают версии по содержимому; import map сохраняет единственный экземпляр общих модулей при относительных и динамических импортах. Генератор: `scripts/version_frontend.py`.

Проверки: 226/226 модульных тестов локально и на серверном Python 3.10; 5/5 живых разнообразных сценариев (8 этапов), подбор с вопросом/защитой от инъекции, демосделка до подписания, контроль FAQ/смены города/остановки. В демосделке одна карточка лимита находилась перед подборкой; повторных сообщений агента в серверной истории не обнаружено. Реальные телефонные вызовы в тестах не выполнялись.

Специальный живой сценарий: первоначальный лимит и оплата → подборка → уточнение пожеланий без повторного подтверждения → новый лимит с одним подтверждением → карточка звонка без поздних финансовых вопросов. Он прошёл на стенде и через публичный сайт (`5f4b61e914c1`). Порядок карточек: `red_lines → payment → selection → selection → red_lines → selection → call`.

Браузерные проверки 1440/390 px: Enter/Shift+Enter, старт и голос, формы/финансы, история и навигация, 4/4 группы карты/аудиожизненного цикла и повторной доставки SSE. Загрузка неверсионированных JS-модулей запрещалась тестовой заглушкой. Дополнительно опубликованный фронтенд проверен с подменённым API: 17 модулей загружены с версиями, Enter создал один запрос, при поиске была одна плашка без дублирующей карточки.

# Личная ИИ-мастерская

Мастерская — дополнительный аналитик nanobot, доступный из того же сайта. Основной агент покупки сохраняет свой провайдер и сценарий. Файлы от покупателя не требуются: мастерская берёт принадлежащий ему диалог, профиль и отмеченные квартиры.

Разработка мастерской ведётся в `feature/nanobot-workshop`. Ветка `all_branch` возвращена на `4fd82ec`, до добавления nanobot. После обновления БД до v3 запускать старое приложение из `all_branch` на этой базе нельзя; для рабочего сайта используется ветка мастерской.

## Три задачи

1. Ремонт понравившихся квартир: три диапазона для каждой квартиры — минимальный, косметический и капитальный. Полей бюджета ремонта и единственной ставки больше нет. Площадь, диапазоны ставок и запас считает код; фото помогают объяснить видимые работы. Ставки — демонстрационные допущения, не найденные котировки подрядчиков.
2. Сравнение понравившихся квартир: состояние по описанию и фото, метро, школы, садики, парки, площадь и цена. Инфраструктура проверяется сервером; неизвестное не превращается в отсутствие. Рекомендация зависит от пожеланий. Стоимость ремонта к покупке не добавляется.
3. Исследование рынка: реальные объявления по последним принятым условиям выбранного диалога, медианы и распределения, ограничения выборки. Контекст обновляется перед запуском и при смене профиля; незавершённое применение пожеланий не запускает исследование по прежним условиям. Явная галочка исследует весь город без фильтров и показывает это в подписи, сохраняя основной профиль.

Новые задания используют версию анализа 2. Сохранённые задания и вопросы по ним продолжают использовать исходные данные и расчёты своей версии; архивные отчёты не переписываются. У каждого нового отчёта видны условия его снимка. В основном подборе есть кнопка «Показать понравившиеся» с количеством отметок: она возвращает отмеченные квартиры из разных страниц без разрешения на звонок.

Результат: ответ аналитика, таблица проверенных исходных расчётов, Excel и CSV. Дополнительные HTML/SVG доступны только как вложения для скачивания. Работа, прогресс, отмена и предыдущие отчёты доступны в модальном окне. Исследование не звонит продавцам и не меняет подбор.

## Доступ и модель

API требует авторизацию, флаг premium в БД и точное совпадение адреса `darkyhat@mail.ru`. Одного скрытия кнопки недостаточно: чужие задания, диалоги и файлы недоступны на сервере. Даже premium=true у другого аккаунта не открывает пилот.

`WORKSHOP_LLM_PROVIDER=deepseek` выбирает DeepSeek для мастерской. `gigachat` выбирает GigaChat без замены nanobot или прикладных функций. Модуль `backend.llm.factory.get_provider` возвращает общий интерфейс сообщений, инструментов и результатов; для GigaChat мост сохраняет `functions_state_id`. Ключи и OAuth остаются на сервере. Основная настройка `LLM_PROVIDER` независима.

Интерфейс мастерской нейтрален к провайдеру. Реально использованный провайдер записывается в задании и техническом аудите; скрытие марки в UI не означает подмену сведений об архитектуре.

## Исполнение

1. Сервер проверяет доступ и принадлежность диалога, фиксирует неизменяемый снимок. Отметки текущей страницы передаются явно и сверяются с доступными объектами.
2. Предметная проверка допускает задачи недвижимости, ремонта и расходов на жильё. Смешанные посторонние задачи отклоняются; неясные требуют уточнения.
3. Для рынка сервер получает объявления существующим адаптером, проверяет условия и фиксирует ограничения охвата. Для анализа нужно хотя бы шесть подтверждённых объявлений.
4. Сервер вычисляет базовые суммы. Проверенный код в контейнере готовит исходные таблицы Excel/CSV, после чего nanobot выполняет Python для анализа снимка и может дополнять документы. Агент получает точную структуру данных и компактные исходные метрики. Основные суммы отдельно показываются из серверных расчётов. Текстовые выводы модели не являются независимой оценкой недвижимости или сметой.
5. Хост проверяет структуру результатов, соответствие базовых метрик, предметную область ответа и формат файлов. Excel не содержит формул, макросов и внешних ссылок; CSV защищается от исполнения формул.

Песочница — отдельный Docker-контейнер на задание, nanobot-ai 0.4.1, Python 3.12. Непривилегированный UID, read-only корень, network=none, сброшенные capabilities, no-new-privileges. Ограничения: 640 МБ памяти без дополнительного swap, 0.75 CPU, 64 процесса, временные папки, размер файлов. Производственная БД, `.env`, Docker socket и каталоги других пользователей не монтируются. Записываемого каталога хоста у контейнера нет: документы передаются ограниченным каналом stdout.

Единственный канал к модели — выделенный Unix socket с host-side мостом: разрешён только `run_python`, ограничены размер контекста и число запросов. Мост сам добавляет ограничения и выбирает провайдера; контейнер не получает ключи. Код из контейнера не исполняется на хосте.

OpenShell сейчас не используется: на проверенном сервере Landlock ABI 1, требование OpenShell — ABI не ниже 3. Ядро не менялось. Замена среды исполнения изолирована адаптером sandbox; подключение OpenShell требует подходящего хоста и отдельной проверки. Docker-изоляция не даёт такой же политики контроля системных вызовов и файлов, как OpenShell.

## Состояние и ограничения пилота

Задания и история сохраняются в SQLite, повтор ID не запускает новый расчёт. Одна работа исполняется одновременно, максимум три принятых активных задания, 30 новых заданий в сутки. Nanobot ограничен восемью итерациями и 12 обращениями через мост. Выполнение контейнера ограничено тремя минутами; получение источников и предметные проверки имеют собственные таймауты.

После перезапуска незавершённая работа получает статус interrupted; платные обращения автоматически не повторяются. Отмена останавливает задачу и удаляет контейнер. Срок хранения отчётов пока не ограничен автоматическим удалением; это небольшой закрытый пилот, объём следует контролировать.

Тематическое ограничение обеспечивается проверками запроса/ответа и ограниченными данными и инструментами. Оно не является математической гарантией поведения LLM. Нет произвольного доступа в интернет, загрузки файлов, установки пакетов по просьбе пользователя, банковских и юридических операций.

## Проверки и выпуск

Локальный критерий выпуска: `python scripts/check_release.py --report-dir /tmp/workshop-gate`. Браузер: `tests.e2e.workshop_server` и `tests.e2e.workshop_ui`, отдельно регрессия основного интерфейса `flexible_server` / `flexible_ui`.

Настоящий nanobot и выбранный провайдер: `python -m tests.e2e.live_workshop --provider deepseek --report /tmp/workshop-deepseek.json`; аналогично `--provider gigachat`. Без `--real-sources` объявления синтетические, модель и Docker настоящие. С `--real-sources` используются реальные источники. Тест создаёт отдельную временную БД, не выдаёт права производственному аккаунту и не вызывает телефонию.

Миграция v3 добавляет premium и историю мастерской. Перед выпуском проверяется копия рабочей SQLite: целостность, внешние ключи и неизменность исходных столбцов всех прежних таблиц. После обновления схемы откатывать код можно к совместимому checkpoint `0af2491`, а не к старому приложению со схемой v2. Контейнер следует закреплять проверенным тегом/ID через `WORKSHOP_IMAGE`, а не случайным latest.

## Уточняющие вопросы и Markdown

После готового отчёта доступно поле «Вопрос по исследованию». Вопрос создаёт связанное задание с теми же объявлениями, условиями, расчётными допущениями и датой снимка. Повторного сбора рынка нет. Nanobot получает историю предыдущих вопросов/ответов и может выполнить новые вычисления над исходной выборкой. Основной профиль и отметки не изменяются. Каждый ответ и его файлы сохраняются отдельно; обсуждение восстанавливается через «Мои исследования» после перезагрузки.

В одной беседе до 60 записей, включая исходное исследование. Следующий вопрос принимается после завершения предыдущего. Повтор ID идемпотентен. Используются существующие записи заданий и JSON-снимки, новая миграция не требуется. В контекст модели передаются последние четыре обмена с ограничением объёма прежних ответов; текущий запрос и проверенные метрики сохраняются полностью. Сохранённые сообщения доступны в снимке, полные ответы — в интерфейсе исследования. Сжатие промежуточных вычислений использует ту же ограниченную выдержку, чтобы не вернуть длинную историю обратно в контекст. Дневной лимит распространяется и на вопросы.

Отчёты поддерживают заголовки, выделение, списки, таблицы, код и ссылки Markdown. Marked 18.1.3 и DOMPurify 3.4.17 поставляются локально с лицензиями и SHA-512 исходного npm-архива. HTML очищается по списку разрешённых тегов; изображения, скрипты, обработчики событий и опасные ссылки не вставляются. Широкие таблицы прокручиваются внутри отчёта. Чекбокс исследования всего города выровнен с многострочной подписью на узких экранах.

## Анализ фотографий и телефонный режим

Nanobot получил инструмент `inspect_photos(listing_ids)`. Он доступен для квартир из снимка исследования: URL от модели не принимается. Сервер использует сохранённую галерею либо открывает объявление Циана, если исследование было создано до сохранения фотографий. Известный источник не превращается в произвольный веб-доступ контейнера. За задачу исследуются до трёх новых квартир, до четырёх снимков каждой. Предыдущие успешные наблюдения переиспользуются в уточнениях.

Сервер ограничивает HTTPS-домены изображений (`cian.ru`, `cian.site`, `cdn-cian.ru` и их поддомены), редиректы, объём загрузки и разрешение. Pillow проверяет изображение, убирает метаданные и уменьшает его до 1280 px по длинной стороне. Ключи остаются на хосте. Снимки передаются через общий метод `analyze_images`: DeepSeek использует `DEEPSEEK_VISION_MODEL=deepseek-flash`, независимо от основной текстовой модели; GigaChat Ultra получает временные вложения через Files API с последующим удалением. Для GigaChat используется общая очередь запросов.

Результат — видимые признаки отделки, замечания с номерами фотографий и ограничения. Фасады, планы и рендеры не считаются доказательством фактического состояния квартиры. Невалидный ответ модели и недоступное изображение дают «не проверено», а не отрицательную оценку. Проверка тематики не оценивает наличие фотографий: это обязанность инструмента.

Наблюдения, дата, URL и SHA-256 обработанных снимков сохраняются в задании. В интерфейсе показаны изученные фотографии и фактический охват; в Excel добавляется лист «Фото и состояние». Nanobot может посчитать дополнительный сценарий ремонта с объяснением допущений; исходная ставка пользователя и базовые факты молча не изменяются. Это анализ видимой отделки по выборочным снимкам, а не обследование скрытых коммуникаций.

## Поставка раздельных режимов

Новые оценки ремонта используют три демонстрационных диапазона: минимальный 5–10 тыс. ₽/м², косметический 12–22 тыс., капитальный 30–50 тыс.; запас 15% показывается в расчёте. Это заданные допущения с пояснением состава работ, без выдачи за актуальные цены подрядчиков. Неизвестная площадь не превращается в нулевые затраты. Проверенные таблицы Excel/CSV и таблица интерфейса содержат все три варианта; цена покупки не складывается с ремонтом.

Сравнение получает метро из объявления и проверки школ, садов и парков от существующего геомодуля. Минимальная цена, минимальная цена за м² и максимальная площадь вычисляются отдельно кодом, включая равенства и неизвестные значения. Наблюдения по фото сохраняются в сокращённой истории агента, а не только в файле, который модель могла забыть прочитать. Последняя ошибка Python в сравнении вызывает ограниченное исправление; незавершённый расчёт не публикуется как успешное сравнение.

Контекст мастерской содержит актуальные принятые условия без внутренних полей первоначального запроса. Краткое описание строится заново из этих условий. Перед запуском браузер запрашивает контекст повторно, а сервер всегда формирует снимок из сохранённого состояния выбранного диалога. Пока новая реплика не применена, возвращается понятное ожидание вместо исследования по прежнему профилю. Смена профиля обновляет открытую мастерскую. На отчёте указаны условия его снимка; старый формат ремонта/сравнения помечен архивным.

## Согласованная выборка исследования рынка

Обнаружена разница между подбором (четыре подтверждённые квартиры и две непроверенные из 399 полученных записей) и исследованием (одна подтверждённая). Исследование повторно собирало только первые страницы, обрезало сырые данные до 150 строк и проверяло инфраструктуру у первых 30 объектов до фильтрации. Дополнительный жёсткий порог шести подтверждённых объявлений превращал небольшой объём данных в ошибку.

Теперь исследование по текущим условиям фиксирует весь доступный пул выбранного диалога при принятии задания. Оно повторно применяет актуальные условия тем же вычислителем, что и основной поиск; сортировка, количество показанных карточек, страницы и лайки не сужают исходный пул. Подтверждённые и непроверенные объявления сохраняются отдельно. Основные медианы и таблицы считаются только по подтверждённым, а интерфейс явно показывает обе численности и число объектов в расчёте. Лимит 150 применяется после проверки условий.

Когда сохранённый поиск даёт подтверждённые варианты, повторного сбора и проверки карты нет. При отсутствии такой выборки выполняется новый сбор; инфраструктура проверяется у кандидатов после базовой фильтрации. Явное исследование всего города остаётся отдельным сбором без фильтров покупки. Последующие вопросы используют прежний снимок исследования; изменение профиля не меняет принятые и архивные задания.

Один–пять подтверждённых объектов допускают сравнение с явным предупреждением о малой выборке, без выводов о всём рынке и трендах. Если подтверждений нет, ошибка называет число непроверенных и сохраняет охват. Непроверенный объект не становится подтверждённым ради запуска анализа. Сервер передаёт модели готовые численности охвата, медианы и цены за м² каждой квартиры; числовые итоги также выводятся интерфейсом независимо от текста модели.

# Личная ИИ-мастерская

Мастерская — дополнительный аналитик nanobot, доступный из того же сайта. Основной агент покупки сохраняет свой провайдер и сценарий. Файлы от покупателя не требуются: мастерская берёт принадлежащий ему диалог, профиль и отмеченные квартиры.

Разработка мастерской ведётся в `feature/nanobot-workshop`. Ветка `all_branch` возвращена на `4fd82ec`, до добавления nanobot. После обновления БД до v3 запускать старое приложение из `all_branch` на этой базе нельзя; для рабочего сайта используется ветка мастерской.

## Три задачи

1. Ремонт понравившихся квартир: площадь × указанная пользователем ставка, резерв, покупка вместе с ремонтом. Начальные 30 000 ₽/м² и 15% — редактируемые сценарные допущения, а не расценки подрядчика.
2. Сравнение понравившихся квартир: цена, площадь, цена метра, ремонт и общая стоимость, выводы и неизвестные параметры.
3. Исследование рынка: реальные объявления по профилю выбранного диалога, медианы и распределение по комнатности, ограничения выборки. Отдельная явная галочка позволяет исследовать весь город, не изменяя основной профиль.

Результат: ответ аналитика, таблица проверенных исходных расчётов, Excel и CSV. Дополнительные HTML/SVG доступны только как вложения для скачивания. Работа, прогресс, отмена и предыдущие отчёты доступны в модальном окне. Исследование не звонит продавцам и не меняет подбор.

## Доступ и модель

API требует авторизацию, флаг premium в БД и точное совпадение адреса `darkyhat@mail.ru`. Одного скрытия кнопки недостаточно: чужие задания, диалоги и файлы недоступны на сервере. Даже premium=true у другого аккаунта не открывает пилот.

`WORKSHOP_LLM_PROVIDER=deepseek` выбирает DeepSeek для мастерской. `gigachat` выбирает GigaChat без замены nanobot или прикладных функций. Модуль `backend.llm.factory.get_provider` возвращает общий интерфейс сообщений, инструментов и результатов; для GigaChat мост сохраняет `functions_state_id`. Ключи и OAuth остаются на сервере. Основная настройка `LLM_PROVIDER` независима.

Интерфейс мастерской нейтрален к провайдеру. Реально использованный провайдер записывается в задании и техническом аудите; скрытие марки в UI не означает подмену сведений об архитектуре.

## Исполнение

1. Сервер проверяет доступ и принадлежность диалога, фиксирует неизменяемый снимок. Отметки текущей страницы передаются явно и сверяются с доступными объектами.
2. Предметная проверка допускает задачи недвижимости, ремонта и расходов на жильё. Смешанные посторонние задачи отклоняются; неясные требуют уточнения.
3. Для рынка сервер получает объявления существующим адаптером, проверяет условия и фиксирует ограничения охвата. Для анализа нужно хотя бы шесть подтверждённых объявлений.
4. Сервер вычисляет базовые суммы. Проверенный код в контейнере готовит исходные таблицы Excel/CSV, после чего nanobot выполняет Python для анализа снимка и может дополнять документы. Агент получает точную структуру данных и компактные исходные метрики. Основные суммы отдельно показываются из серверных расчётов. Текстовые выводы модели не являются независимой оценкой недвижимости или сметой.
5. Хост проверяет структуру результатов, соответствие базовых метрик, предметную область ответа и формат файлов. Excel не содержит формул, макросов и внешних ссылок; CSV защищается от исполнения формул.

Песочница — отдельный Docker-контейнер на задание, nanobot-ai 0.4.1, Python 3.12. Непривилегированный UID, read-only корень, network=none, сброшенные capabilities, no-new-privileges. Ограничения: 640 МБ памяти без дополнительного swap, 0.75 CPU, 64 процесса, временные папки, размер файлов. Производственная БД, `.env`, Docker socket и каталоги других пользователей не монтируются. Записываемого каталога хоста у контейнера нет: документы передаются ограниченным каналом stdout.

Единственный канал к модели — выделенный Unix socket с host-side мостом: разрешён только `run_python`, ограничены размер контекста и число запросов. Мост сам добавляет ограничения и выбирает провайдера; контейнер не получает ключи. Код из контейнера не исполняется на хосте.

OpenShell сейчас не используется: на проверенном сервере Landlock ABI 1, требование OpenShell — ABI не ниже 3. Ядро не менялось. Замена среды исполнения изолирована адаптером sandbox; подключение OpenShell требует подходящего хоста и отдельной проверки. Docker-изоляция не даёт такой же политики контроля системных вызовов и файлов, как OpenShell.

## Состояние и ограничения пилота

Задания и история сохраняются в SQLite, повтор ID не запускает новый расчёт. Одна работа исполняется одновременно, максимум три принятых активных задания, 30 новых заданий в сутки. Nanobot ограничен восемью итерациями и 12 обращениями через мост. Выполнение контейнера ограничено тремя минутами; получение источников и предметные проверки имеют собственные таймауты.

После перезапуска незавершённая работа получает статус interrupted; платные обращения автоматически не повторяются. Отмена останавливает задачу и удаляет контейнер. Срок хранения отчётов пока не ограничен автоматическим удалением; это небольшой закрытый пилот, объём следует контролировать.

Тематическое ограничение обеспечивается проверками запроса/ответа и ограниченными данными и инструментами. Оно не является математической гарантией поведения LLM. Нет произвольного доступа в интернет, загрузки файлов, установки пакетов по просьбе пользователя, банковских и юридических операций.

## Проверки и выпуск

Локальный критерий выпуска: `python scripts/check_release.py --report-dir /tmp/workshop-gate`. Браузер: `tests.e2e.workshop_server` и `tests.e2e.workshop_ui`, отдельно регрессия основного интерфейса `flexible_server` / `flexible_ui`.

Настоящий nanobot и выбранный провайдер: `python -m tests.e2e.live_workshop --provider deepseek --report /tmp/workshop-deepseek.json`; аналогично `--provider gigachat`. Без `--real-sources` объявления синтетические, модель и Docker настоящие. С `--real-sources` используются реальные источники. Тест создаёт отдельную временную БД, не выдаёт права производственному аккаунту и не вызывает телефонию.

Миграция v3 добавляет premium и историю мастерской. Перед выпуском проверяется копия рабочей SQLite: целостность, внешние ключи и неизменность исходных столбцов всех прежних таблиц. После обновления схемы откатывать код можно к совместимому checkpoint `0af2491`, а не к старому приложению со схемой v2. Контейнер следует закреплять проверенным тегом/ID через `WORKSHOP_IMAGE`, а не случайным latest.

Для демонстрации: войти этим аккаунтом, обновить страницу, отметить квартиры «Нравится», открыть «ИИ-мастерская · Премиум». Выбрать подбор и одну из трёх задач. Загружать файлы не требуется. ## Уточняющие вопросы и Markdown

После готового отчёта доступно поле «Вопрос по исследованию». Вопрос создаёт связанное задание с теми же объявлениями, условиями, расчётными допущениями и датой снимка. Повторного сбора рынка нет. Nanobot получает историю предыдущих вопросов/ответов и может выполнить новые вычисления над исходной выборкой. Основной профиль и отметки не изменяются. Каждый ответ и его файлы сохраняются отдельно; обсуждение восстанавливается через «Мои исследования» после перезагрузки.

В одной беседе до 60 записей, включая исходное исследование. Следующий вопрос принимается после завершения предыдущего. Повтор ID идемпотентен. Используются существующие записи заданий и JSON-снимки, новая миграция не требуется. В контекст модели передаются последние четыре обмена; полная доступная история остаётся в интерфейсе. Дневной лимит распространяется и на вопросы.

Отчёты поддерживают заголовки, выделение, списки, таблицы, код и ссылки Markdown. Marked 18.1.3 и DOMPurify 3.4.17 поставляются локально с лицензиями и SHA-512 исходного npm-архива. HTML очищается по списку разрешённых тегов; изображения, скрипты, обработчики событий и опасные ссылки не вставляются. Широкие таблицы прокручиваются внутри отчёта. Чекбокс исследования всего города выровнен с многострочной подписью на узких экранах.

Проверка обновления `88beffd`: 408 Python-тестов, 47 JavaScript-проверок и 128 команд нагрузки прошли локально. Браузерные сценарии на 1440/390 px проверили форматирование, защиту от HTML-вставок, положение чекбокса, два вопроса и восстановление после перезагрузки. Настоящий nanobot выполнил 6/6 сценариев на каждой из двух моделей: три исходные задачи, два последовательных вопроса и отказ вне тематики. Объявления в этом повторном корпусе синтетические; новая реальная выдача не требовалась, поскольку здесь проверяется сохранение исходного исследования. Runtime обновления `58705f4712e1fbe4`.
